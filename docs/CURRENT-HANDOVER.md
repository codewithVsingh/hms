# Bilingual UI, patient history and cancellation

This is a consolidated development baseline. Existing 001–016 migrations are preserved. Apply 017 and 018 to an existing development DB at migration 016; fresh DB: all 18. Run `supabase/tests/verify_cancellation_history.sql` as database owner in staging. No migration was executed in this environment.

## Patient references and records
- New generated patient numbers use `PT-` plus at least six decimal digits. New appointment references use `BK-` plus seven uppercase base-36 characters. Sequences and unique constraints avoid collisions, references are not secrets, existing references remain valid, rescheduling preserves the reference. UUIDs remain internal keys.
- Doctor > Patient history search: exact MRN, active authorized care assignment and branch required; timeline is paginated (25 visits), includes released/signed clinical records and own authorized drafts, vitals, diagnoses, prescriptions and archived copies. Cross-branch history and identity linking/merge are not implemented. Reception should reuse the existing MRN; independently registered records are not automatically merged by name/phone.
- Staff > Prescription register: issued prescriptions persist automatically; reception sees administrative metadata and may log handover or attach a paper copy to an encounter. Clinical instructions cannot be edited by reception. Paper uploads require the approved private malware scanner, max 4 MB PDF/PNG/JPEG. Assigned clinician verifies the archived copy; this is not a certified digital signature.

## Language
EN is the default, Hindi selector persists preference locally and passes language between configured website and portal domains. Static common labels, public navigation, key booking/auth controls, new workflow screens and many dashboard labels have curated Hindi strings. This is not complete localization: dynamic CMS content, clinician-authored notes, medicine names, dates, provider UI and remaining English labels/errors need separate review. Do not machine-translate medical instructions. No Hindi-indexable routes or hreflang are provided. PWA remains portal-only; no clinical offline caching.

## Cancellation
- Public site links to `/manage-booking`. Verify mobile (existing verified session can be reused), enter booking number and exact patient number OR name. Ownership check is mandatory. Only online bookings owned by the verified account are self-service; unlinked reception bookings and unclear payments require reception.
- Admin > Cancellation policy: default late fee INR 0; free cancellation at least 24 hours prior. Configure a legally/clinically reviewed policy and publish matching terms. New booking stores policy version, fee and cutoff; older bookings retain zero deduction unless originally configured. Patient acknowledges current policy before booking. Changes apply prospectively, not retrospectively.
- Quote displays exact paid amount, late deduction capped at amount paid, and refundable amount. Free/unpaid booking deduction zero. Confirm rechecks status, policy, slot and amounts under locks, stores cancellation ledger and releases slot. Existing older cancel endpoint returns a review-required response; direct RPC execution revoked. Duplicate confirmations return existing outcome. The sample INR 500 paid / INR 50 fee / INR 450 refund is fictional, not an actual hospital fee.
- Default `HMS_AUTO_POLICY_REFUNDS=false` or unset: refund is requested, admin approves the persisted exact amount in finance. Optional `true` enables automatic claim/initiation after cancellation and maintenance runs; do not enable until Razorpay test validation, hospital policy approval and worker setup. Unknown provider outcomes are kept for review; never blindly retry refund creation. Provider receipt/payment ID/amount checked; maintenance can locate processing refunds by receipt. Refund timing 5–7 working days after initiation (Razorpay normal estimate), subject to bank/payment method. No 3–5 day promise. Offline payments, multiple captures, chargebacks, uncertain payments and staff exceptions need manual review. No general-purpose arbitrary partial refund or settlement accounting.

## Validation
Offline source-component Chromium harness 30/30 (6 screens, 5 language/viewport combinations), including Hindi/English quote and confirm, exact refund arithmetic, patient search and responsive width. Earlier screenshots moved into `review/archive/earlier-screenshots`; new captures under `review/screenshots`. Standalone preview uses a React compatibility adapter; it does not perform real OTP/booking/refund or clinical storage. The environment has no installed Next dependencies, registry access or live PostgreSQL/Supabase/Razorpay credentials. Full build/typecheck, SQL application, browser PWA install and live E2E/authorization/financial reconciliation are mandatory before launch. See staging cases below.

## Required staging acceptance
1. Fresh 18 migration run; verify original UUID refs still resolve; parallel booking creates distinct BK refs; staff registration generates PT ref; rescheduling preserves BK/MRN. Check references under concurrent insert.
2. Patient A must not discover B's booking via reference or name/MRN, even through direct RPC. Test anonymous, wrong OTP, unlinked reception booking and another branch. Verify API and DB auth independently.
3. Test policy acknowledgement; update policy then submit stale version; expect rejection. Policy changes do not alter prior appointments. Test no fee, fee less than amount, fee equal to amount, free window boundary and unpaid booking. Compare integer paise values.
4. Concurrent cancel vs payment capture/reschedule, double-click cancel, quote changed, expired slot and provider timeout. Confirm one persisted cancellation and at most one refund request. Payment must be captured and amount verified before refund. Test admin approval, auto mode off/on, provider receipt mismatch, duplicate maintenance, failed/pending/processed refund and late captures. Compare Razorpay dashboard and invoice ledger. Never use live keys for these tests.
5. Test reception handover without clinical access, doctor assigned/unassigned and wrong branch timeline; old notes and issued Rx immutable. Reject oversize, wrong magic bytes, failed scan, unconfigured scanner; check file access/audit. Test full history paging and existing MRN reuse.
6. Validate curated Hindi on real Android/iOS/desktop, screen reader, keyboard focus in cancellation dialog, actual portal install and generic offline fallback. Review medical content and all policy translations before publishing.
